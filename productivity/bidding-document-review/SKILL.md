# Bidding Document Technical Review (招标技术需求书评审)

## 触发条件

用户要求评审/审查/修改/优化以下类型的文档时**必须加载此 skill**：

- 招标技术需求书
- 技术规范书 / Technical Specification
- 招标文件中的技术部分
- RFP / RFQ 技术章节
- 战略合作技术协议

关键词信号：招标、投标人、验收标准、交付物、技术方案、投标文件、评标。

## 评审维度（7 个审查层次）

按优先级从高到低依次检查：

### P0 — 可验收性（合同执行风险最高）

每条技术要求必须是**可量化、可测试、可验收**的。模糊量词是最大的问题源。

| 模糊词 | 严重程度 | 改法 |
|--------|---------|------|
| "海量""大量""众多" | 🔴 致命 | → ≥N (TB/条/GB) |
| "高并发""多通道" | 🔴 致命 | → ≥N (QPS/通道数) |
| "大体积""长时间" | 🟠 高 | → ≥N (GB/小时) |
| "良好的""较强的" | 🟠 高 | → 删除或量化 |
| "行业标准" | 🟠 高 | → 指定具体标准号/软件名称 |
| "偏差≤X%" | 🔴 致命 | → 必须指定对标基准、测试方法和测试数据集 |
| "准确率≥X%" | 🔴 致命 | → 必须指定测试数据集、数据量、故障类别数 |

**示例修正**：
```
✗ "所有声学指标计算结果与行业标准专业分析软件结果偏差≤5%"
✓ "以 B&K PULSE 为基准，选取 5 组实测 ATFX 文件盲测：SPL(A)≤0.5dB，1/3倍频程各频带≤1.0dB"
```

### P1 — 编号与结构体系

检查项：
- 是否有跳号（如 2.4.6→2.4.8，缺 2.4.7）→ 修复为连续编号
- 编号是否重复（如两个"（5）"）→ 修复为递增
- 章节编号格式是否统一（如 2.1.1存储 vs 2.4.1 存储 → 统一加空格）
- 所有主要章节是否使用相同的编号层级（如第五章也应使用 5.1/5.2 而非直接(1)(2)）

### P2 — 措辞强制力

招标文件应使用**强制措辞**，避免选择性和建议性措辞：

| 弱措辞 | 强制措辞 |
|--------|---------|
| 支持… | 须提供… |
| 可… | 必须… |
| 建议… | 应当… |
| 优先考虑… | 要求… |
| 宜采用… | 须采用… |

特别警惕 "/"（或）连接的选择性条款，如"搭建分布式/单机数据库"——这给投标人留下了低配履约的空间。

### P3 — 法律与合同效力

- 验收标准是否有基准数据集定义？
- 验收方法是否明确（第三方检测/现场演示/盲测）？
- 知识产权归属是否清晰（源代码交付+著作权）？
- 质保期和运维服务是否有量化指标（响应时间≤X小时，服务期≥Y年）？
- 违约条款是否对应可验收指标？

### P4 — 术语一致性

- 全文同一概念是否使用同一术语？（如"本地大语言模型"vs"本地大模型"）
- 缩写是否在首次出现时定义了全称？（如 ASAM、ATFX、NVH、SPL、Leq、FRF）
- 是否存在术语错误？（如"数据库字典"应为"数据字典"）
- 建议增加"术语与定义"章节

### P5 — 格式与标点

- 中英文空格是否一致（中文与英文单位之间、数字与单位之间）
- 标点符号是否统一（全角括号 vs 半角括号）
- 多余空格（如"倍频程 、 1/3倍频程"中的空格）

### P6 — 结构逻辑

- 是否存在重复章节（同一需求在不同位置反复出现）？
- 是否存在"功能需求"与"方案要求"混淆（第二章写功能，第六章写方案）？
- 章节顺序是否符合"总则→分模块→格式→交付→验收→方案"的逻辑？

## 验收标准审查清单

当文档包含性能指标时，逐条检查以下问题：

| 检查项 | 样例 |
|--------|------|
| 基准软件/设备是否指定？ | "B&K PULSE" vs "行业标准软件" ✓ vs ✗ |
| 测试数据集是否指定？ | "1,000 条实测数据" vs "数据验证" ✓ vs ✗ |
| 环境/硬件是否指定？ | "CPU 32核/128GB内存" vs "高性能服务器" ✓ vs ✗ |
| 测试方法是否指定？ | "第三方盲测" vs "测试" ✓ vs ✗ |
| 通过/失败阈值是否明确？ | "≤0.5dB" vs "基本一致" ✓ vs ✗ |

## 输出格式

评审完成后输出 Markdown 报告，按优先级分级：

```markdown
# 技术需求书修改意见

---

## 🔴 P0：可验收性问题（不改可能在验收时产生合同纠纷）

| 位置 | 原文 | 问题 | 修改建议 |
|------|------|------|---------|
| 第 X 行 | ... | ... | ... |

---

## 🟠 P1：编号与结构

...

## 🟡 P2：措辞强制力

...

## 🟢 P3~P6：格式与细节

...

## 修改优先级总表

| 优先级 | 问题数 | 影响 |
|--------|--------|------|
| 🔴 P0 | N | 合同纠纷风险 |
| 🟠 P1 | N | 专业性质疑 |
| 🟡 P2 | N | 约束力不足 |
| 🟢 P3~P6 | N | 专业性印象 |
```

## 常见陷阱

1. **只改内容不改编号**：插入新条款后未更新后续编号 → 产生跳号
2. **验收标准改了但没改数据集**：说"准确率≥95%"但没说是用什么数据测的 → 等于没写
3. **忽视"/"选择性条款**："支持A/B"意味着投标人可选低配方案
4. **重复条款不同表述**：同一需求出现在 1.3 和第三章，后期修改只改了一处 → 合同漏洞
5. **弱措辞在验收时无法扣分**："支持"不是"必须"，投标人没实现也无法认定为违约
