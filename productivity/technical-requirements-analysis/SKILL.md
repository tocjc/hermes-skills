# 技术需求文档分析与方案设计

系统性地阅读中文技术需求文档，逐条输出对应解决方案，涵盖开源选型、授权分析、难点评估与开发周期规划。

## When to Invoke

- 用户提供了 `.docx` / `.md` / `.pdf` 格式的技术需求文档（招标技术要求、软件规格书、系统设计方案等）
- 用户要求"逐条分析"、"逐条给出解决方案"、"给出技术方案"
- 内容涉及多个技术模块（数据库、算法、AI、部署等）
- 需要评估开源软件选型和授权合规性
- 需要分析项目难点并给出开发周期

## Workflow

### Step 1: 读取与解析文档

**.docx 文件** — 使用 `read_file` 工具自动提取（Hermes 内置 python-docx 解析）：
```python
from hermes_tools import read_file
result = read_file("/path/to/file.docx")
content = result.get("content", "")
```

**.md / .pdf** 文件同理，PDF 自动经由 pymupdf 提取。

### Step 2: 需求结构化分类

按模块/章节将需求分组。例如 NVH 系统的典型模块分类：

| 模块 | 典型标题 |
|------|---------|
| 数据库模块 | "数据库模块开发要求"、"数据存储" |
| 知识库模块 | "知识库""专家系统" |
| 算法/分析模块 | "信号处理""频率分析""声品质" |
| 训练模块 | "大数据训练""深度学习""模型训练" |
| AI/LLM 模块 | "大语言模型接口""智能诊断" |
| 业务模块 | "下线检测""测评""售后" |
| 通用配套 | "架构要求""部署要求""文档交付" |

### Step 3.6: 硬件配置建议（可选）

涉及 GPU 训练、大模型推理或高性能计算的模块，给出推荐配置表：

| 用途 | 配置 | 数量 | 预算参考 |
|------|------|:---:|---------|
| 数据库+应用服务器 | 32核/128G RAM/4TB NVMe | 2 | 高配 |
| 对象存储节点 | 24核/64G RAM/100TB HDD | 3 | 中配 |
| GPU训练+推理 | A100-80G / 昇腾910B | 1-2 | 高配 |
| LLM推理节点 | RTX 4090 24G×2 | 1 | 中高配 |

### Step 3.7: 风险评估矩阵（可选）

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|:-----:|:----:|---------|
| 专有格式版本不兼容 | 中 | 高 | 实现版本检测+兼容层 |
| GPU采购周期长 | 中 | 高 | 提前下单，先用CPU方案过渡 |
| 国产化OS兼容性 | 中 | 中 | 提前验证+检查清单 |
| 模型精度未达预期 | 低 | 中 | 标注数据+回归验证 |

### Step 3.8: JSON 配置规则引擎（下线/测评模块）

当需求中包含"通过 JSON 配置文件定义测评规则并自动执行"，补充规则引擎设计：

```json
{
  "rule": [
    {
      "name": "噪声超标判定",
      "analysis_type": "SPL",
      "params": {"weighting": "A", "time_constant": "fast"},
      "threshold": {"max": 85, "unit": "dB(A)"},
      "pass_condition": "value <= threshold.max"
    }
  ]
}
```

实现要点：规则解析器 → 多阶段分析链 → 判定引擎 → 报告生成。规则引擎与具体模块（下线/测评/售后）解耦，只需替换参数配置即可复用。

### Step 3: 逐条解决方案生成（核心）

对每条需求，按以下结构输出：

```markdown
| 要求 | 分析 | 解决方案 |
|------|------|---------|
| (N) 原文 | 技术难点/考量 | 具体方案 + 技术选型 + 实现细节 |
```

**解决方案模板**：
1. **技术选型**：具体到库/框架/版本号
2. **实现路径**：简述怎么实现
3. **开源/商业说明**：如果是开源组件，说明授权协议
4. **国产化备选**（如适用）：信创环境下替代方案

### Step 4: 开源软件授权分析

对选择的每个开源组件，整理授权表：

| 软件 | 用途 | 授权协议 | 商业闭源兼容 | 国产化备选 |
|------|------|---------|------------|-----------|
| PostgreSQL | 关系数据库 | PostgreSQL License | ✅ | 人大金仓 |
| MinIO | 对象存储 | AGPLv3（商业例外） | ✅ | 杉岩数据 |
| Elasticsearch | 搜索引擎 | Elastic License 2.0 | ✅ | EasySearch |
| PyTorch | 深度学习 | BSD | ✅ | 昇思 MindSpore |
| vLLM | LLM推理 | Apache 2.0 | ✅ | - |
| Milvus | 向量数据库 | Apache 2.0 | ✅ | - |
| RabbitMQ | 消息队列 | MPL 2.0 | ✅ | RocketMQ |
| Redis | 缓存 | BSD | ✅ | Tair |
| Neo4j Community | 知识图谱 | GPLv3 | ⚠️ 有传染风险 | NebulaGraph (Apache 2.0) |

**关键检查点**：
- AGPLv3 软件确认是否有商业例外（如 MinIO）
- GPLv3 组件不可在闭源商业软件中链接使用
- MIT/BSD/Apache 2.0 协议安全

### Step 5: 项目难点评估

按难度等级 `⭐` 到 `⭐⭐⭐⭐` 评估每个核心模块的技术风险：

| 难点 | 评级 | 应对策略 |
|------|:----:|---------|
| 海量数据（100TB+） | ⭐⭐ | 分布式存储+冷热分层+分区表 |
| 专有格式解析（ATFX等） | ⭐⭐ | 正则块解析替代 XPath |
| 信号处理算法（FFT/PSD等） | ⭐⭐ | SciPy + librosa 已有成熟实现 |
| 声品质算法（Zwicker模型） | ⭐⭐⭐ | pySDM/mosqito + 声学专家验证 |
| 阶次分析 | ⭐⭐⭐ | 角域重采样 + Kalman滤波 |
| 高精度回放链路 (±2.0dB) | ⭐⭐⭐⭐ | 专业ASIO声卡 + FIR补偿滤波 |
| LLM本地部署 + 领域微调 | ⭐⭐⭐ | INT4量化 + vLLM + LoRA |
| 国产OS兼容性 | ⭐⭐⭐ | 提前验证 + 原生部署脚本 |

## Pitfalls

### ❌ 读取 .docx 时出现乱码
Python-docx 读取带复杂格式的文档时可能遗漏表格嵌套内容。读取后手动检查结构完整性，如有缺失改用 `python-docx` 的 `.tables` API 或 pandoc 转换后重新提取。

### ❌ 开源协议传染性问题
Neo4j Community Edition 使用 GPLv3，在商业闭源软件中直接链接使用会触发"传染性"义务。**解决方案**：使用 NebulaGraph (Apache 2.0) 替代，或购买 Neo4j Enterprise 商业授权。同理，MongoDB 的 SSPL 协议也不适合闭源商业产品。

### ❌ 忽略国产化合规
涉及政府/国企项目时，需提前确认信创目录内的数据库（人大金仓、达梦、GaussDB）、操作系统（麒麟、统信）和芯片（飞腾、鲲鹏、昇腾）兼容性。

### ❌ 需求遗漏
技术文档中常包含分散在"验收要求""通用要求""其他"等章节的非功能性需求。建议用 checklist 兜底扫描：
- [ ] 性能指标（吞吐/延迟/并发）
- [ ] 安全要求（加密/审计/权限）
- [ ] 部署要求（国产OS/离线/容器化）
- [ ] 文档交付（设计/部署/运维/API/测试）
- [ ] 维护期（SLA/响应时间/升级路径）
