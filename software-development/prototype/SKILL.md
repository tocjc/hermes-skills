# Prototype Skill — 原型开发

源自 Matt Pocock 的 `prototype` 技能。构建一次性原型来回答设计问题。原型是**扔掉的代码**，用来回答一个问题。

## 触发场景

- 需要验证一个状态模型或逻辑是否合理
- 需要探索 UI 应该长什么样
- 不确定某个设计方向，需要快速试一下
- 用户说"做个原型看看"、"验证一下这个想法"

## 选择分支

先确定要回答什么问题：

### 分支 A: "这个逻辑/状态模型对吗？"

构建一个**单一的 HTML 文件**，包含：
- 自由操作的按钮
- 标签页式引导教程
- 推动状态机通过各种难以在纸上推理的路径
- 非开发者也能操作

### 分支 B: "这个应该长什么样？"

生成**多个完全不同的 UI 变体**，放在同一个路由上，通过 URL 参数或浮动底栏切换。

## 通用规则

1. **从第一天起就是扔掉的**，并明确标记。原型代码放在它要验证的模块旁边，但命名上让读者一眼看出是原型
2. **易于启动** — 一个命令运行，或双击 HTML 文件
3. **默认无持久化** — 状态在内存中。持久化是原型要验证的东西，不是它应该依赖的
4. **跳过打磨** — 不测试、不处理错误（除了让原型可运行所必需的）、不抽象
5. **暴露状态** — 每次操作后，显示完整的状态，让用户看到变化
6. **完成后捕获** — 把验证后的决策融入真实代码，原型本身提交到临时分支，在 issue 中留下上下文指针

## 与 Hermes 配合

- `prototype` 验证想法 → 然后将验证后的决策融入 `plan-implement-review`
- 原型验证的逻辑可以内联到 `to-spec` 中

## 常见陷阱

- ❌ **不确认分支** — 逻辑分支和 UI 分支产出完全不同的东西
- ❌ **不标记为原型** — 别人会以为是生产代码
- ❌ **加持久化** — 默认不需要持久化
- ❌ **加测试和错误处理** — 原型是扔掉的，不要投入
- ❌ **不暴露状态** — 用户需要看到每次操作后的变化
